# CLORIX — MASTER DEVELOPMENT DIRECTIVE
## 0. Mission
Build **Clorix**, tagline **From lead to loyalty.**, a genuine, responsive full-stack CRM that a recruiter, teacher or friend can try and operate. A smaller set of complete workflows is preferable to many superficial features. This is a non-commercial portfolio evaluation release, not an enterprise certification or a client production CRM. Design for maintainable later expansion. Do not claim implemented features before evidence.

## 1. Authority and workflow
Read AGENTS.md, DOs_AND_DONTs.md, PRD, DESIGN_SYSTEM, LANDING_ANIMATIONS, ACCESS_MODEL, ARCHITECTURE, DATA_MODEL, API_CONTRACT, BUSINESS_RULES, SECURITY_PRIVACY, TESTING, DEPLOYMENT and RELEASE_CHECKLIST. Follow explicit locked choices over older concept images. Inspect git status and existing app before scaffolding. Initialize app only if absent. Keep docs and implementation synchronized. Use one modular TypeScript application, one dedicated Postgres database, one deployment. Pick stable compatible package versions, pin lockfile, record choices. No speculative framework upgrades.

## 2. Implement the product in vertical slices
- Foundation: app shell, tokens, real schema/migrations, server validation, secure sessions, workspace isolation and permissions. Create a deterministic synthetic seed. Establish DB integration tests early.
- Access: clear public landing; no-invite **Try live sandbox** that creates an isolated, persisted synthetic workspace, bounded by durable abuse controls and expiration. Normal login/registration for private evaluation accounts with the configured policy; owner can create scoped team invitation links if implemented as specified. All core sandbox actions genuinely write to PostgreSQL; no localStorage business data, no shared writable demo workspace. Clearly disclose sandbox data and expiry, do not request real client data. If provisioning is unsafe/unavailable, fix or report blocker; do not label a read-only walkthrough as live sandbox.
- Customer lifecycle: leads, contacts, companies, deals, tasks, notes and activity timeline. Search, filter, sort, paginate and validate; edit/archive and appropriate safe deletes. Lead qualification and atomic conversion with linked entities; no duplicates on retry. Customer relationship page brings related records together.
- Pipeline: default stages, open/won/lost state, real drag and drop plus accessible move menu, transactionally persisted transitions, history, stage counts and totals; handle concurrent changes and rollback failed optimistic UI. Deals can be won/lost/reopened under documented rules.
- Work management: task due dates, priority, completion, follow-up list, manual call/meeting/email/note log; no actual external messages sent. In-app reminders derived from due tasks. Workspace members and simple owner/member roles.
- Reporting: actual server-side metrics, date filters, stage breakdown, forecast and closed-won trend from persisted values; no fabricated numbers. Exact currency math; no cross-currency summation. CSV import preview/errors/confirmation and safe authorized export. Global search across accessible records with keyboard access.
- AI: private CRM must work without AI. Deterministic follow-up queue and insights are mandatory, transparently labeled rules-based. Optional real Gemini lab restricted to immutable fictional sample payloads and specifically authorized eligible adult testers; disabled by default, no arbitrary inputs or real CRM content to external AI. Do not add a disabled button masquerading as an available feature. See AI_POLICY.md. This optional module is not a core release gate.
- Frontend: follow locked Clorix hybrid branding. Build a cinematic marketing hero with perspective product panels and an accessible animated lifecycle narrative; alternate light and dark sections. App sidebar dark, content predominantly white/light, forest/lime/mint selective accents. No busy neon dashboard. Desktop/tablet/mobile. Real forms, loading, empty, error, confirmation, undo where safe. No dead navigation, placeholder routes, fake claims, stock logos or made-up testimonials.

## 3. Security and correctness
Never expose keys, customer fields or passwords in logs, commits, client env or screenshots. Server-side authorization on every object and query; explicit workspace context from authenticated membership, not trusted client IDs. PostgreSQL runtime role non-owner, no bypass RLS; force policies for tenant tables and use transaction-local settings under pooling, verify cross-tenant read/write denial. Auth boundary, session lifecycle, role changes and guest provisioning are tested. Use mature auth library and avoid bespoke crypto. Validate inputs and limits; protect CSV injection, CSRF, XSS, tenant enumeration, brute-force and quota bypass. All user mutations enforce role and active session; no background scraping, campaigns or outbound automation. Test with two tenants and independent accounts. Public sandbox is synthetic only and expires; private data never sent to unpaid AI.

## 4. Efficient testing and delivery
Use unit, real PostgreSQL integration, browser and hosted acceptance checks per TESTING.md. Target ~150–200 meaningful checks if time permits; counts are not a substitute for passing essential workflows. All mandatory acceptance scenarios pass, no unresolved critical/high release-blocking defects; optional features hidden or transparently excluded. Measure actual performance with modest synthetic load and distinguish local/warm/cold/hosted. Verify no fake charts, no static demo substituted for real app, no secrets, no unrelated resources changed. Capture actual screenshots on desktop/mobile after implementation. Test hosted sandbox and private account access, reload/re-login persistence, CRUD, lead conversion, pipeline transitions, reports, CSV, isolation and graceful failures. If a provider is unavailable, core app still works. Do not run tests against other projects or destructive migrations on production.
